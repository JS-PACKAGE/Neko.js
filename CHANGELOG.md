# Changelog

## Unreleased

Measurements below are single observations on one macOS arm64 machine (10 cores, Node.js 26.7.0, CPU, pinned default profile) that was shared with unrelated heavy processes (1-minute load average roughly 20-35); they are not guarantees and an idle machine was never available. Greedy text, constrained and validation-only structured outputs were identical to 1.6.1 on the exercised prompts, and the real-model state-reuse smoke and a path-image inference passed.

- Performance: Node ONNX sessions no longer spin-wait between operators (`session.intra_op.allow_spinning=0`). In three alternating runs against 1.6.1's settings on the shared machine, decode fell from about 68-162 to about 46-55 ms/token, prefill from about 190-580 to about 135-200 ms, and process CPU time from about 620-1050 to about 290-340 ms per generated token. Idle-machine decode latency with this setting was not measured; spinning is what 1.6.1 used.
- Performance: nucleus (`topP < 1`) sampling selects the top-K logits by insertion instead of sorting the whole 248,320-entry vocabulary on every token: about 125 ms to about 1.2-2 ms per token for `topK` 50 (microbenchmark, CPU time). Results match a full stable sort, including ties and `-Infinity` masks; `topK` above 256 or 0 still sorts.
- Performance: constrained decoding copies a precomputed bitmap for ordinary string pieces instead of one callback per allowed token, and the token trie is built from packed arrays without per-token objects. Per-token grammar masking fell from about 6.6 to about 1.5-2.8 ms CPU; first-use trie construction for the 248,056-piece vocabulary fell from about 830 to about 400-490 ms. The string-continuation bitmaps were compared with the previous per-token check on the real vocabulary and differed nowhere across all eight UTF-8 continuation classes.
- Performance: cached model files are read in 1 MiB chunks instead of 64 KiB. For the 484 MB decoder payload, read-and-hash fell from about 1050-1270 ms to about 420-600 ms; hashing every pinned file at load fell from about 560 to about 355 ms. Every byte of every new process is still verified.
- Performance: model session creation starts while the tokenizer and processor resources are parsed. Warm engine load fell from about 700 (674-808) to about 645 (621-657) ms; together with the above, warm `Neko.create` plus a one-token inference fell from about 1.7-2.1 s to about 1.4-1.6 s wall and from about 4.6-5.5 s to about 2.8-3.0 s CPU.
- Performance: document indexing extracts lexical terms about 1.5-2 times faster for Latin text (a CJK-free fast path, no per-word Unicode-property test, no intermediate arrays); building a 500-document, 8 KB-each index fell from about 885 to about 660 ms CPU. Term output is unchanged (20,000 random mixed-script strings compared with the previous implementation).
- Performance: local image files are read into one exact-size buffer rather than 64 KiB chunks that are concatenated, halving peak memory for the read; files that change size during the read still fall back to bounded chunked reads.
- Performance: browser bundles are built with whitespace and identifier minification (source maps retained). `dist/browser/neko.js` fell from about 2.06 MB to about 1.06 MB (gzip about 435 KB to about 305 KB). Syntax minification is deliberately off: it folds the computed `node:` imports into literals that consumers' bundlers cannot resolve (the packed-consumer check caught this). Verified with the packed-consumer artifact check, the 21 browser contracts on Chromium, Firefox and WebKit, and the Chromium WebGPU smoke (text, image and report inference completed with no page errors).
- Performance: `validatePage`, `snapshotPage` and `selectPage` no longer scale roughly cubically with the number of containers and paragraphs. Container ancestry was re-walked for every container with a linear paragraph-membership scan per hop; each parent link is now checked once with set lookups (same checks and error messages). For a page of 200 sections (1,400 paragraphs, extracted from HTML) `validatePage` fell from about 8.5 s to about 4 ms, `snapshotPage` from about 10.6 s to about 40 ms and `selectPage` from about 1.7 s to about 12 ms; the cubic term made pages of a few thousand paragraphs effectively unusable.
- Performance: zero-inference extractive reports hash the whole checkpoint once per retained paragraph only when an `onCheckpoint` callback can observe it; otherwise the checksum is computed at the final (and error) save. For 1,200 paragraphs generation fell from about 10.4 s to about 0.16 s (it was quadratic). Callbacks, events and the final checkpoint and report checksums are unchanged.
- Performance: constrained decoding checks string-enum prefixes by binary search over a sorted copy built once per enumeration (and keeps the sorted remainder for unique-item enums) instead of scanning every candidate per byte. Document questions put every paragraph ID in an enum: with 2,000 IDs, warm masking of a 27-token answer fell from about 183 to about 96 ms CPU (about 6.8 to about 3.6 ms/token; microbenchmark against the real vocabulary). A differential test compares the accepted prefixes with a brute-force reference.
- Performance: `DocumentIndex.updateDocument` and `removeDocument` no longer re-tokenize and re-hash the whole corpus. Unchanged documents keep their version ID, chunks and cached canonical JSON; untouched term postings are shared with the previous state (never mutated, so in-flight searches keep a consistent view) and only the terms of changed, added or removed chunks are rebuilt, in the same posting order a rebuild produces; replacements that change most of the corpus still rebuild. On a 500-document, 8 KB-each index, one update fell from about 720 to about 50-65 ms CPU. A differential test compares chunks, posting order, average length and search results with a from-scratch build after each of several updates, additions and removals, and a golden test pins the snapshot IDs produced by 1.6.1 (IDs and persisted formats are unchanged; 1.6.1 also imports snapshots exported by this build).
- Performance: claim audits look cited paragraphs up by ID instead of scanning the snapshot's paragraph list for every citation (frozen SDK snapshots are indexed once), so report generation and `validateStructuredReport` no longer grow quadratically with paragraph count. For a 4,800-paragraph extractive report, generation fell from about 3.8 to about 1.4 s CPU and validation from about 1.7 to about 0.6 s; both now scale linearly. Audit results are unchanged.
- Performance: `DocumentIndex.getDocument` and `documentIds`-restricted searches look documents up by ID instead of scanning the document list, which was quadratic in the number of requested IDs. A search restricted to 5,000 document IDs of a 5,000-document index fell from about 1.1 s to about 5 ms.
- Performance: text-only `planInference` no longer re-reads, re-hashes (SHA-256 of the 19 MB `tokenizer.json`), parses and rebuilds the tokenizer on every call. The verified tokenizer, chat template and configuration are loaded once per instance and shared by planning and the engine, so a later engine load also skips them; they are dropped whenever the engine is released (explicit release, `cache.model.clear()`, `engineTtlMs` expiry, or each request when engine caching is disabled) and on disposal. `askDocuments` plans once per retrieved chunk: with `topK: 100` (13 selected, 87 omitted) its planning fell from about 162 s to about 6 s on the busy test machine, with the same selection. Planning and actual inference reported the same input tokens inline and in a worker. The cost is about 70 MB of JavaScript heap held between plans.
- Performance: HTML table extraction no longer compares every cell with every header cell of the table, nor rescans the row group for every cell. Headers are indexed by the rows, columns and row group they can apply to, then the same geometry test decides in the same order. A 2,000-row, 8-column table (16,008 cells) extracted in about 0.4-0.6 s instead of about 2.9-3.5 s. Extracted pages and snapshot IDs were identical to the previous build on 1,500 random tables (spans, `rowspan="0"`, scopes, explicit `headers`), and a test compares header relations with a whole-table reference scan.
- Performance: image preprocessing flattens vision patches with a strided copy instead of Transformers.js 4.2.0's generic 9-axis `Tensor.permute`, which divided every element index by each axis. Only the engine's own `Qwen2VLImageProcessor` instance is changed. Planning a 4000×3000 JPEG (1,216 input tokens) took about 360 ms CPU instead of about 990 ms on Node; greedy image inference produced the same text and input tokens as before, and a test compares processor output bit-for-bit with upstream. A headed Chromium WebGPU smoke completed image, text and report inference with the change; headless Chromium closed the page during the first inference on this machine at this and at earlier commits.

## 1.6.1 — 2026-10-03

- Performance: on Node, each pinned ONNX payload file is hashed once per installed runtime instead of four times per load (prefetch plus three loader requests); unchanged files are recognised by device, inode, size, mtime and ctime, and new processes still verify every byte. Measured warm model load fell from about 2.3 s to about 1.3 s on macOS arm64. The cache no longer calls `chmod` on files that already have mode `0600`, which would have advanced ctime.
- Performance: Node ONNX sessions now use `os.availableParallelism()` intra-op threads. On a 4 performance + 6 efficiency core Apple machine this raised prefill about 25% (about 213-238 to about 290 tokens/s) and lowered decode about 12% (about 28 to about 25 tokens/s); the best value depends on hardware.
- Performance: structured calls reuse an engine-private decoder state for their fixed system instruction (text-only, at least 32 tokens, no explicit `reuse`). Time to first token for a 115-token structured prompt fell from about 460-540 ms to about 130-160 ms on a hit, with identical output in the exercised cases. `reuseCacheInfo()` gains `prefixEntries`, `prefixBytes`, `prefixHits` and `prefixMisses`.
- Performance: the constrained-decoding token trie uses typed arrays; building it for the 248,056-piece vocabulary took about 270 ms (was about 337 ms) and about 54 MB of external/array-buffer memory instead of about 230 MB of JavaScript heap.

## 1.6.0 — 2026-10-03

- **Fix (affects 1.5.0):** a first-use model download from Hugging Face could not complete. Observed against the live Hub on 2026-10-03: non-LFS files redirect same-origin to `/api/resolve-cache/models/<id>/<revision>/<file>`, which the default network policy denied (`POLICY_DENIED`), and interrupted CDN downloads could never resume because the signed redirect URL changes per request and was compared as part of the object location. The exact pinned model/revision/file `resolve-cache` path is now trusted (size/SHA-256 verification unchanged) and resume matches by origin and path, including partial staging written by 1.5.0. Verified by a complete live prefetch of the pinned default profile with every file SHA-256 checked.
- **Fix (CI, Windows):** the 1.5.0 remote CI run failed 3 of 22 jobs, all `windows-2025`, in `npm run test:quality`. The CLI test built its script path from `URL.pathname` (`D:\D:\a\...`), and Git's CRLF conversion changed the byte-hashed quality fixtures (`LOCAL_FIXTURE_INTEGRITY`). The path now uses `fileURLToPath`, and `.gitattributes` marks `scripts/quality/fixtures/**` as `-text`. The full remote CI matrix (19 of 22 jobs; the other 3 are opt-in real-model lanes that are skipped) passes on commit `ef501ed`, including all three `windows-2025` jobs.
- **Fix (Windows):** Node image inputs such as `D:\photo.png` were mistaken for URLs with a one-letter scheme and rejected as non-HTTP; drive-letter paths are now read as local paths (the same canonical file authorization applies). The cache permission test no longer asserts POSIX mode bits on Windows.
- Add opt-in hybrid document retrieval: caller-supplied `DocumentEmbedder`, `DocumentIndex.searchHybrid` and `askDocuments({ embedder, embedding })` combine BM25 with cosine ranking by reciprocal-rank fusion. Neko.js bundles no embedding model; embedder output is validated as untrusted, vectors are cached per index by content version under a fixed 128 MiB bound, and retrieval remains non-exhaustive.
- Add `runToolLoop`: a bounded select, approve/execute, feed-back and re-infer loop over `inferTools` and `executeToolCalls`. Approval stays mandatory and sequential; calls requested by the terminal selection are returned, never executed.
- Add opt-in `onEvent` observability: content-free request lifecycle and engine-load events (ids, timings, token counts, error codes, model identity). Observer failures never change request results; worker forwarding is best-effort.
- Document every 1.5.0 API and the items above in the English and Traditional Chinese usage guides.
- Packaging checks now fail on sync-conflict duplicate files (the working tree is iCloud-synced and produced `* 2`/`* 3` copies) and bundle `neko.js`, `neko.js/documents`, `neko.js/web` and `neko.js/report` with esbuild under browser conditions.
- Verified on macOS arm64, Node.js 26.7.0 CPU, default profile: 217 Node tests, 27 quality-tool tests, 21 browser contracts (Chromium, Firefox, WebKit), site smoke, packed-artifact check, the state-reuse smoke against the real model (cached continuation equal to baseline text and usage, branch isolation, abort leaves the cache unchanged, vision feature hits), one synthetic image OCR, one synthetic scanned-PDF OCR and native PDF extraction without inference. Remote CI passes its contract matrix on Linux, macOS and Windows for Node 22, 24 and 26 (the real-model lanes are opt-in and were not run). Observed, not asserted as quality: document QA on the PDF fixture returned `insufficient-evidence`, and a 128-token budget truncated structured JSON (`STRUCTURED_OUTPUT`). Not verified: browser WebGPU, browser PDF extraction, the new hybrid retrieval with a real embedding model, and real-model inference on other platforms.
