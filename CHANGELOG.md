# Changelog

## Unreleased

- Reports: the `zh-TW` language check weighs Han characters against Latin words instead of Latin letters (a claim fails when Latin words × 2 exceed Han characters). Product names and identifiers made ordinary Traditional Chinese fail every retry, for example `TypeSafe AI 是後來 ChatGPT 誕生的基石。` (17 letters against 8 Han characters). Han-free, Simplified and Latin-dominated text still fails.
- Examples (extension): only paragraphs whose every sentence passes the report language's check are read. On a mixed Chinese/English README the model restated the other language's sentences, and every retry failed the check. Stages may also write up to 1024 tokens (was 512): the summary of that README restated its Chinese sources nearly verbatim and was cut off as incomplete JSON on every retry.
- Examples (extension): the report language now follows the text being read instead of the page's declared `lang`. A Chinese page declaring `lang="en"` asked the model for English, which the 0.8B model answered in Chinese, so every section failed the English language check (`Report claim did not satisfy the requested English language check`) after its retries. In a headed Chromium WebGPU run the sample page served with `lang="en"` now finished its report in Traditional Chinese.

## 1.9.1 — 2026-11-08

- Browser: a `modelSource.baseUrl` inside the installed package that holds the SDK bundle (a browser extension's own `chrome-extension:` origin) is accepted and read in place. Every load still hashes each file against the pinned size and SHA-256; nothing is copied into Cache Storage, no network policy or model request is involved, `clear()`/`importBundle()` reject with `POLICY_DENIED`, and `diagnostics().backend` is the new `'package'`. HTTP(S) sources, including same-origin ones, are unchanged.
- Examples (extension): the model now ships inside the extension, so the loopback mirror, options page, `storage` permission and fixed `key` are gone. `npm run build:extension [-- --cache-dir=<root>]` downloads the model through the Node SDK when needed, re-verifies each packaged copy, adds `THIRD_PARTY_NOTICES.txt` and icons, sets `minimum_chrome_version` 120, and writes `dist/neko-extension-<version>.zip` (about 690 MiB) for Chrome Web Store upload, with a privacy policy in `examples/chrome-extension/PRIVACY.md`. In a fresh headed Chromium WebGPU profile the sample page report finished in about 15 s with no request outside the page's origin and an empty extension Cache Storage; report text still contained errors. Not published.

## 1.9.0 — 2026-11-08

Measurements below are single observations on one macOS arm64 machine (Apple M5, Node CPU or headed Chromium WebGPU, pinned default profile); they are not guarantees. Nothing here claims output quality.

- **Behavior change (reports, browser WebGPU):** two consecutive images are now also described in one batched decode under the same conditions as other batched stages: on browser WebGPU, `inferStructuredBatch` accepts rows with one prepared, untiled image, each row prefilling and encoding only its own image while upstream computes every row's multimodal RoPE positions from the batch's image grids. There, the next image is prepared before the current one is described; a preparation failure is still handled, under the image failure policy, in its original turn, and both image `stage-start` events precede their completion events. The gain is small: in alternating actual default-worker WebGPU two-image reports the image stages took about 2.6-2.7 s instead of 2.8-2.9 s, with identical generated content. Node CPU keeps describing images one at a time: batching them there saved about 0.25 s but its batched arithmetic changed one word of one image description.
- **Behavior change (reports):** the summary and conclusion now decode together under the same conditions as batched sections (no token streaming, sampling or per-call hard deadline, enough aggregate budget, and a conclusion that fits its context); the conclusion's input never depends on the summary. Both `stage-start` events now precede their `stage-complete`/`stage-error` events, and a failed row is retried alone under the usual authorization. In actual default-worker WebGPU two-image reports, the summary and conclusion together took about 6.0 s instead of 7.9 s and whole reports about 15.8 s instead of 17.4-18.0 s (alternating runs), with identical generated content; actual Node worker reports produced identical content with no measurable change in duration (CPU-bound).
- **Behavior change (browser):** `createNeko` now also defaults to `execution: 'worker'` in browsers, so ONNX Runtime session creation, WebGPU dispatch and prefill no longer run on the page's main thread by default. In an actual WebGPU two-image report with the option omitted, every 16 ms page timer fired within 20 ms and no load-time gap reached 50 ms (inline: 25-41 ms report gaps and 100-170 ms load gaps), with identical generated content. Only the default falls back: if the SDK worker cannot be created or initialized (for example a CSP that blocks `blob:` workers, a policy that denies the `worker` script, or no WebGPU inside workers), the instance is created inline with exactly the inline behavior and errors (verified with `worker-src 'none'`, which produced the identical report inline); an explicit `execution: 'worker'` still fails. Relative image URL strings passed to a browser worker now resolve against the creating page, as inline, instead of the worker module's URL. Pass `execution: 'inline'` to keep the previous behavior.
- **Behavior change (Node):** `createNeko` now defaults to `execution: 'worker'` in Node. Native ONNX Runtime 1.30 runs every session call synchronously on the calling thread, so inline Node execution blocked the event loop for each prefill and decode step. On one loaded machine the same text report measured event-loop lag p50/p99/max of about 24/48/1,878 ms inline against about 6/9/71 ms in a worker, with identical generated content. Default instances no longer take the realm-local inline owner (so they no longer collide with `RUNTIME_BUSY`) and report `execution.mode: 'worker'`; pass `execution: 'inline'` to keep the previous behavior.
- Performance (browser WebGPU): reuse bind groups for repeated (layout, buffer-range) bindings instead of creating one per kernel dispatch. Entries are hashed and verified exactly against the stored descriptor; identities are per-object, so a released native handle reassigned to another buffer or layout never aliases a cached group. Chains, non-buffer resources and oversized entry lists take the upstream path, and two bounded generations (16,384 entries each) age groups out without per-hit Map churn. An actual inline text report preserved generated content while `createBindGroup` calls fell from 1,084,232 to about 66,000 (about 1.6 s to 0.1 s inside the native call); three counterbalanced comparisons on a loaded machine kept the candidate ahead on total time, timer/animation-frame gaps of 24 ms or more and long tasks. Timings on that machine drifted strongly, so no stable end-to-end speedup is claimed.
- Performance (browser WebGPU): upload uniforms straight from the heap view with an element offset, clear released registry slots instead of deleting them, and remember each buffer's `BigInt` size/usage. An allocation-sampled actual text report fell from about 587 MiB to about 429 MiB of cumulative sampled allocation with identical content. This is not a retained-memory or stable wall-time claim.
- Performance: release a decode step's raw logits buffer when the next decoder run starts on every runtime, not only Node. onnxruntime-web still copies the 1 MB logits row into a fresh buffer per step, and that external memory forced a full mark-compact about every 50 tokens. GPU-resident outputs are never read. A GC-traced actual inline WebGPU text report preserved generated content with major collections down from 19 to 8 (117 ms to 43 ms of pauses) and background marking from 852 ms to 264 ms; timer gaps of 32 ms or more fell from 7 to 2. No stable total-latency claim is made.
- Performance (browser WebGPU): batched section decoding no longer compacts a GPU-resident decoder state when one row finishes. Compaction downloaded every state tensor (about 76 MB for two rows of the pinned model), gathered on the CPU and uploaded again, which stalled the main thread and triggered a full collection at each batch end; a memory-bound GPU decode step costs about the same with the finished row kept as ignored padding. CPU-resident state (Node) still compacts, and reported usage is unchanged. An actual inline text report preserved generated content with both end-of-batch readback bursts gone.
- Performance: build all eight ordinary-string token bitmaps inside the cooperative token-trie setup instead of on the decode step that first opens a JSON string or leaves a UTF-8 sequence pending. In an actual inline WebGPU text report they no longer appear during generation; constrained masks and output are unchanged.
- Performance: a reuse snapshot of GPU-resident decoder state keeps the freshly downloaded buffer instead of copying it again. Generation only reads that buffer as the next run's input, and disposing the working tensor never touches it; CPU-resident (Node) state is still cloned. An actual inline WebGPU text report preserved generated content with the snapshot copy gone from its main-thread profile.
- Performance: constrained decoding no longer re-walks the structural token trie for every step inside an ordinary JSON string when the outcome cannot depend on the string's text (no enumeration, no `maxLength`, `minLength` already met, and no enclosing `enum`/`uniqueItems`); the result is cached per immutable grammar frame and pending UTF-8 class. String length bounds are decided from UTF-16 length when possible instead of counting code points on every closing candidate, and object-key continuations are checked without allocating per probed byte. Masks are unchanged (a new test compares cached masks against full parsing as one string grows). In actual Node inline reports, sampled grammar allocation fell from about 400 MiB to about 40 MiB and grammar walk CPU from about 790 ms to about 75 ms; an actual inline WebGPU report spent about 590 ms instead of 1,250 ms in grammar code, with identical generated content in both runtimes.
- Performance: token-trie setup also yields while packing the 248k vocabulary into token bytes, and its slice timer now includes reading the vocabulary. The longest uninterrupted setup slice in a Node measurement fell from about 22 ms to about 14 ms; token bytes and masks are unchanged, and an actual inline WebGPU text report produced identical content.
- Performance: building or updating a document index (`createDocumentIndex`, `updateDocument`, `replaceDocuments`, `removeDocument`, `importDocumentIndex`) yields to the event loop once a slice has run 8 ms, between chunks, documents and posting updates. It was one synchronous stretch: on Node, whose hashing does not yield, and in Chrome alike. Two instrumented actual inline WebGPU text-report comparisons preserved generated content while maximum animation-frame callback gaps fell from 44–60 ms to 28–29 ms; a counter-free comparison measured 57.5 ms versus 29.2 ms. ## 1.8.0 — 2026-11-06

Measurements below are single observations on one macOS arm64 machine (Apple M5, Node.js 26.7.0, Node CPU or headed Chromium WebGPU, pinned default profile) that was shared with unrelated heavy processes; they are not guarantees. Greedy text outputs, tokenizer state, report plans and evidence cut points were compared against 1.7.0 where stated. Report text generated by the 0.8B model from the example pages contained factual errors; nothing here claims output quality.

- Dependencies: the development-only `minimatch` under `@typescript-eslint/typescript-estree` is overridden to 11.0.4 (GHSA-g3hv-75wg-m249, denial of service via globparts amplification; no patched 10.x exists). ESLint's own `minimatch` 3.x is outside the affected range and unchanged.
- Reports: generated text that is exactly a retained source quote (for example the navigation label "3 C" copied verbatim into a key point) no longer fails the requested-language check during generation or validation; such text is source text, not generated prose. A news article with a Traditional Chinese `lang` whose body had no `<main>` failed on that label before.
- Reports: explicitly authorized `retries` now also cover a stage whose output fails the requested-language check (`LANGUAGE_MISMATCH`), as they already did for invalid structured output. The retry prompt already asks for the requested language; without `retries` the error is unchanged.
- Fixed: a generated report from an instance that never created the vision encoder session (a page without images, since the session became lazy) failed validation with "Loaded session configuration is incomplete". Text sessions are still required; the vision session is now optional.
- Browser: runtime files served from the bundle's own non-HTTP origin, such as `chrome-extension://` inside an extension, are no longer rejected as an unsupported protocol. Other schemes, and opaque origins such as `file:` and `data:`, are treated as before.
- Examples: `examples/chrome-extension/` (built with `npm run build:extension`) adds the floating reader button to every http(s) page in Chromium and runs one shared model in an offscreen document. A first click downloaded the model from the loopback mirror; after a restart a page on another origin made no model requests. `serve-model-mirror.mjs --allow-origin` accepts an exact Chromium extension origin.
- Examples: `examples/sample-page/` is a fictional Traditional Chinese web page (navigation, advertisement and footer around a `main` article with a table, a list, an illustration and a chart), and `examples/read-sample-page.mjs` reads it by URL over loopback and prints its `describe` report. `node scripts/serve-examples.mjs` serves the page on loopback for trying the extension below, which adds the reader button; the page itself has none. Node CPU and Chromium WebGPU (extension) runs read the chart values correctly but also misstated facts from the page; see the usage guide.
- Performance (Node): `tokenizer.json` (19 MB) is parsed on a worker thread. Parsing it and building the 248k-entry vocabulary and 247k-entry merge-rank Maps held the main thread, which model loading also needs to create ONNX sessions, for about 0.5 s. The worker returns the Map keys as two strings, and the main thread only builds the Maps, which the bundled Transformers.js BPE constructor now accepts prebuilt (a build-time patch; plain JSON takes the original path). The tokenizer state (vocabulary, merge ranks, special tokens, retained configuration) was identical to the previous build's, as were 2,000 random encodings and greedy outputs inline and in the worker runtime. In four alternating runs on the loaded Apple M5, `load()` took about 0.13-0.25 s less (about 1.08-1.82 s instead of about 1.21-2.06 s) and the planner's process RSS was about 65 MB lower; a first text-only `planInference()` on its own was about equal or up to about 0.07 s slower, and the worker adds about 0.05-0.2 s of total CPU time. If the worker is unavailable or fails, the main thread parses the file as before.
- Performance: report planning and generation split long sentences into evidence quotes in roughly linear instead of quadratic time. Each binary-search probe encoded the whole remaining text to test it against a 192-token budget; probes now replay the pinned tokenizer's pipeline one pre-token at a time and stop as soon as a probe exceeds the budget. The probes and cut points are unchanged (token counts are not monotonic in the slice length): 1,300 random texts split identically to 1.7.0, and plans for 40 random pages and a 100 KB paragraph had identical hashes. Text that NFC would change, text containing added-token content, and other tokenizer pipelines keep full encoding. `planReport` CPU time for one long paragraph on the loaded Apple M5 fell from about 0.6-0.7 to about 0.1-0.2 s at 40 KB, about 7 to about 0.5-0.7 s at 200 KB, and about 25 to about 1.2-1.4 s at 400 KB.
- Performance: `load()` no longer creates the vision encoder session; the first request with images (or `warmup()`) creates it, through the same verified cache, graph patches and session options, so text-only use never pays for it. In three alternating runs on a loaded Apple M5, process RSS after `load()` and one text request was about 0.99-1.0 GB instead of about 1.11-1.12 GB, and load CPU time about 0.2 s lower; greedy text and image outputs were unchanged. Loaded session metadata now lists `vision_encoder` only once it exists, and Transformers.js progress totals reported during `load()` still count the vision files. A failed vision session load fails that request (a corrupted cached vision payload failed the first browser image request with a SHA-256 mismatch while text inference kept working) and the next image request retries. Browser load times in two alternating runs were inconclusive.
- **Behavior change (Node CPU):** `cpuVisionPrecision` now defaults to `'fp32'` for the pinned 0.8B model (other models keep `'fp16'`). The vision MatMuls run in fp32 instead of ONNX Runtime's slower CPU fp16 GEMM; the first token of an 800×600 image request took about 5.8-8.6 s instead of about 6.3-13.6 s in alternating runs on a loaded Apple M5, and greedy descriptions of the test images were unchanged. It costs about 300 MB more resident memory once the vision session exists; pass `cpuVisionPrecision: 'fp16'` to keep the previous behavior.
- Performance (Node CPU): decoding no longer forces a full garbage collection every two or three tokens. onnxruntime-node copies each output into a new `ArrayBuffer`, and every Qwen3.5 decode step returns about 21 MB of recurrent, convolution and attention state that became garbage one step later, so V8's external-memory pressure kept triggering mark-compacts. Once the decoder has consumed state that one of its own runs returned (cache checkouts and snapshots own clones), that state's buffer, and the previous run's logits, are detached so their memory is freed immediately. In three alternating 192-token greedy runs on the loaded Apple M5, full mark-compacts fell from 62-66 to 2-8, total GC pause from about 590-780 to about 24-132 ms, and process CPU time from about 17.4-18.1 to about 15.0-15.2 s; per-token wall time was too noisy on the shared machine to quote. Greedy text, `reuseState` conversations, the structured-output prefix cache, image inference, stop strings and sampling produced the same outputs as 1.7.0, inline and in the worker runtime.
- Performance: constrained decoding inside strings with `maxLength` (OCR text, tool-call IDs, and any caller schema that bounds a string) uses the precomputed ordinary-string token bitmap, filtered by how many code points each token adds, instead of walking the whole 248k-token trie with a cloned grammar state per edge. Masking one token in such a string took about 3 ms instead of about 310 ms (microbenchmark on the real vocabulary); a 68-token structured answer with bounded strings took about 2.9 instead of about 23 s on Node CPU on the loaded Apple M5 (browser runs were not measured), with identical output, and an OCR request returned identical results in about 17 instead of about 25 s. The bounded masks were identical to a per-token grammar check on the real vocabulary at 13 budget/UTF-8 states, and a randomized test compares them with a per-piece reference.
- **Fix (untrusted input, denial of service):** `extractPage` (and so `describe`/`ask` on HTML or URLs) and claim audits (report generation, `validateStructuredReport`, document questions) could spend super-linear time on crafted text. The CSS `url(...)` pattern backtracked cubically on `url(` followed by a long whitespace run (5,000 spaces in one inline `style` took about 51 s), and trailing-comma trimming of `srcset` data candidates, the audit `ranges` pattern on long digit runs (32,000 digits took about 4.7 s) and trailing-punctuation trimming were quadratic. They are now linear scans or a lookbehind with the same matches (300,000 random CSS strings and 500,000 random audit strings were compared with the previous patterns); the same inputs take a few milliseconds, and regression tests use 200,000-character runs.
- Performance: large string enumerations (document questions put every paragraph ID in one) no longer cost time proportional to the enumeration per schema compile and per decoding step. Schema checking compared every pair of `enum` values (the bundled validator's `uniqueItems`); uniqueness is now checked by hashing with the same equality, and 20,000 random schemas were accepted or rejected exactly as before. During constrained decoding, enum membership, number and literal prefixes use indexes built once per enumeration, unique-item remainders are cached per used set, and the code points that may follow a prefix come from binary searches instead of a scan per probed byte. With 20,000 paragraph IDs, compiling took about 7-22 ms instead of about 1.4-2.9 s and masking averaged about 2-7 instead of about 150-240 ms per step (up to about 2.6 s after a comma); with 2,000 IDs about 0.3-1.7 instead of about 7-20 ms. Masks were identical to the previous build at 2,229 states (lone surrogates, U+FFFF and emoji included) and a document question returned the same answer, both checked before the fix below.
- **Fix:** inside enumerated strings and object keys, an `E0` or `F0` UTF-8 lead byte was accepted whenever some remaining candidate continued with a shorter character (for example ASCII), because the lead's payload bits are zero; the next byte then found no continuation, so generation could reach a dead end. Leads now also require a candidate needing that many bytes. Across 2,642 states the only mask change was 8,903 removed tokens, none of which could still reach a candidate.
- Performance (browser): with a `progressCallback`, model loading no longer reads and SHA-256-hashes every cached payload twice. Transformers.js 4.2.0 first matches each file only to read its size for progress totals; cached responses handed to Transformers.js are now verified when their body is first read (header-only lookups cost nothing, and readers still get bytes only after the size and SHA-256 checks), while `status()` and `prefetch()` keep verifying eagerly. In alternating headed Chromium WebGPU runs on the Apple M5, each payload was verified once instead of twice and a first `load()` took about 3.8-4.5 s instead of about 5.6-6.0 s, with the same text output; Node load time was unchanged (about 1.5-1.6 s either way on the loaded machine).
- **Fix (browser):** with 1.7.0, a corrupted cached external-data file (`*.onnx_data`) left `load()` pending forever, because Transformers.js 4.2.0 loads external data inside an `async` Promise executor that drops the read failure. Engine loading now also fails on the first integrity failure the verified cache reports; one flipped byte in the embedding or decoder external data, or in the vision graph, failed the load with the SHA-256 mismatch in about 0.3-2 s. Node already failed such loads during its verified prefetch.
- Performance: greedy decoding takes each token's argmax with a loop that only ever sees `Float32Array` logits. Transformers.js 4.2.0 used its shared `max()`, whose call sites pass many array types, so V8 ran it as a slow polymorphic loop: about 0.84 ms per token over the 248,320-entry vocabulary against about 0.11 ms (microbenchmark). The bundled copy is patched at build time; comparisons and first-index tie-breaking are unchanged, and the build fails if the upstream line changes. On Node CPU, each step's 1 MB logits copy is also released once the next step's logits arrive, so the faster loop does not trade its savings for more full garbage collections (1 instead of about 15 per 192 tokens). Main-thread time outside ONNX Runtime per Node decode token fell from about 1.5-2.0 to about 0.7-0.9 ms in three alternating runs; greedy, structured, image, stop-string and sampled outputs are identical inline and in a worker. Browser bundles carry the same loop and gave the same 120-token WebGPU text; alternating 200-token WebGPU decode runs were within noise (about 22-25 ms/token either way).
- Performance: the first structured inference of each engine builds the 248k-token byte trie about 2.5 times faster (about 250 to about 100 ms in five runs of the build alone). Nodes that reach 16 children, such as the root and common prefixes like a leading space, get a byte-indexed lookup table during construction instead of a linear scan of their sibling lists; the table is discarded afterwards, and the resulting trie arrays are identical to before.
- Performance: report generation hashes the finished report once instead of twice. It validated its own report with the public validator, which re-derived the checksum that had just been computed; the report is now validated before its checksum is set, with the same checks. Extractive reports also skip hashing the final checkpoint when no `onCheckpoint` callback can observe it (a failed report's checkpoint is still hashed). For a 6,000-paragraph extractive report (13 MB of canonical JSON), process CPU time fell from about 1.40-1.81 to about 1.16-1.29 s; `validateStructuredReport` accepts the results and still rejects tampered reports.
- Performance: claim audits extract the claim's lexical values (numbers, units, dates, entities, negation, ranges) once per claim instead of once per cited sentence and again for the reported checks, and reuse them for a quote identical to the claim. Audit results are unchanged (20,000 random claims compared with the previous implementation); a 6,000-paragraph extractive report used about 5-8% less CPU and an audit against a 60-sentence quote about 14% less.
- Performance (Node): content hashes (page snapshots, report and checkpoint checksums, image source IDs, cache keys) use `node:crypto` instead of WebCrypto's `digest`, which hands every call to a thread-pool job with a copy of its input. Hashing 6,000 paragraph-sized inputs took about 4-7 instead of about 32-45 ms (about 7-23 instead of 74-108 ms CPU); `parseStructuredReport` of a 13 MB extractive report fell from about 490-830 to about 405-430 ms and a 6,000-paragraph extractive report from about 1.1-1.3 to about 0.75-0.95 s CPU. Digests are the same SHA-256 hex, so reports and checkpoints remain interchangeable with browsers, which keep WebCrypto.
- Performance: generated reports no longer hash the whole checkpoint after every stage when no `onCheckpoint` callback can observe it; usage and elapsed time are still updated, and a failed report's checkpoint is hashed before it is attached to the `ReportError` (as before, a resumable checkpoint validates). The saved hash grows with the page snapshot (about 120-135 ms for the 8.4 MB checkpoint of a 6,000-paragraph page), so long pages with many stages spent that much per stage.
- Performance: tokenization memoizes the ByteLevel pre-tokenizer, which UTF-8-encoded every pre-token and rebuilt it a character per byte (about half of encoding a prompt). Results depend only on the pre-token; pre-tokens of up to 256 UTF-16 units are cached (at most 65,536 entries, then the cache restarts) and returned as copies. `planReport` for a 750-section page fell from about 5.4-5.6 to about 3.3-3.5 s CPU with an identical plan, and token counts matched the previous build on 600 random multilingual prompts; prompt encoding before inference benefits in Node and browsers alike.
- Performance: report planning (`planReport`, and the plan every generated report builds first) counts prompt tokens without rendering the chat template and re-tokenizing the system instruction for every candidate chunk. The pinned template trims the user text and places it in its own section between special tokens, which the tokenizer encodes independently, so a count is a per-instruction constant plus that section's tokens; the constant is accepted only after it reproduces full rendering on edge-case probes (surrounding whitespace, leading combining marks, special-token text), and text the template treats differently is still rendered in full. `planReport` for a 750-section page fell from about 2.6-2.7 to about 0.8-1.0 s CPU (about 5.5 s before the tokenizer memo above), with identical plans for that page and 40 random multilingual pages.
